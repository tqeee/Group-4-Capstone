This is the ONLY test file — no route/action/component tests exist.
- **Flow lifecycle** (§3.3, rewritten 3 Aug — see Done #19): deposits `PENDING` → ops approve (emails bank details) → `AWAITING_PROOF` → investor submits transfer reference → `PENDING_RECEIPT` → ops confirm receipt → `COMPLETED` + processedDate + ledger rebuild. **COMPLETED is the only status that moves money in the ledger.** Withdrawals skip the transfer dance: `PENDING` → ops approve (balance re-checked at approval time) → `COMPLETED` directly, since OKC is the payer. `REJECTED` reachable from any non-terminal status. The old `APPROVED` status is retired from the Prisma schema but still defined in the Postgres enum (can't drop an enum value without recreating the type).
- **MFA**: ⚠ **two separate AAL2 gates** — ours (the proxy, below) and Supabase's own inside `updateUser`, which blocks password changes at AAL1 for MFA accounts. Both matter to the recovery flow; see Done #27 and #28. Login action redirects to `/mfa` when the `getUser()`-authenticated user has a verified factor (password sign-in is AAL1); proxy (`lib/supabase/proxy.ts`) blocks all but `/mfa` until the verified `aal` claim is `aal2`; `/mfa/setup` enrolls/unenrolls (QR + secret). MFA client events audited via `app/(auth)/mfa/actions.ts`. NEVER call `mfa.getAuthenticatorAssuranceLevel()` server-side — it reads `session.user` from cookie storage and triggers the supabase-js "could be insecure" warning; derive the state from `getUser().user.factors` + `getClaims().claims.aal` instead.
- **Auth data rule**: authorization decisions server-side use `supabase.auth.getUser()` (Auth-server-verified; proxy does this per request, so deleted users drop immediately) or `getClaims()` (signature-verified JWT; used in layouts/actions where a network hop per render is overkill). Never read the user off a stored session.
- **Ingestion** (§3.2): `app/(operations)/data-import/actions.ts` — CSV → papaparse → validate → `deal.createMany skipDuplicates` (idempotent by ticket) → ImportBatch record → ledger rebuild. Accepts BOTH broker formats: numeric dataset-5.4 codes AND the firm's real workbook format (`sample data portal.xlsm`, sheet "5.4 Dummy Data"): string `type`/`entry` ('buy'/'sell'/'balance', 'IN'/'OUT' — mapped via DEAL_TYPES/ENTRY_TYPES), `time` as Excel serial days (46098.23… → epoch offset 25569) with `time_msc` (unix ms) preferred when present, unnamed leading index column tolerated. `type=balance` rows (broker deposits/withdrawals) are EXCLUDED from import with a message telling ops to record them as fund flows; `rebuildFundLedger` also filters `type != 2` defensively. Samples: `public/sample-data/sample-data-portal.csv` (faithful conversion of the firm workbook: 564 trades + 1 balance row, 17 Mar–8 Apr 2026, total P&L −16,028.12 — verified to the cent against the source) and `broker-deals-2026-04-09.csv` (old numeric format, adds one day, net +606.95).
- **Statements**: `app/api/statements/[month]/route.ts` generates CSV from ledger for the signed-in investor; Documents page lists real months.

It clears the authenticator ONLY — never the password — so it restores self-service without handing anyone an account. ⚠ `admin.mfa.*` is marked `@expermental` in supabase-js but round-trips fine here. `listUsers()` doesn't return `factors`, and per-user calls would be one request each, so `listUsers` reads `auth.mfa_factors` directly in a single `$queryRaw` (wrapped in try/catch — MFA state is not worth 500ing the user list over). Verified against the real dev server with throwaway users: recovery POST → 303 + cookie, MFA account sees the challenge and NOT the form, non-MFA account unaffected, `challengeAndVerify` then `updateUser` succeeds, and after an admin 2FA reset the same user reaches the password form. 29. **Idle session timeout — 10 min, warning at 5 (3 Aug, VERIFIED 9/9 server-side + in-browser)**: the portal had NO auto-logout of any kind; a session lasted until sign-out or cookie clear, because the proxy silently refreshes the JWT on every request. Supabase's own **Inactivity timeout** setting is the obvious home for this but is **Pro-plan only** ([docs](https://supabase.com/docs/guides/auth/sessions)) — and even on Pro its check runs only "whenever a session is refreshed next", so the docs concede *"the actual duration of a session is the configured timeout plus the JWT expiration time"* (i.e. a 15-min timeout really means up to 75 min at the default 3600s JWT). The community workaround that dominates search results — a custom `auth.storage` adapter that self-expires — assumes tokens in `localStorage` and **does not apply here** (we're on `@supabase/ssr` httpOnly cookies). So it's enforced in **our** proxy, which already authenticates every request and so checks on the actual request rather than the next refresh. New `lib/auth/idle.ts` holds the constants (`IDLE_TIMEOUT_MS` 10 min, `IDLE_WARNING_MS` 5 min, `IDLE_HEARTBEAT_MS` 2 min) + `idleMillisFrom()`. `lib/supabase/proxy.ts` reads the `okc-last-activity` cookie, and over budget → `signOut({scope:'local'})` (local so an idle desktop doesn't kill the user's phone) → 307 `/login?timeout=1` (API routes get `401 {"error":"Session expired"}`); otherwise it re-stamps the cookie before the MFA/role gates so their redirects carry it. `redirectTo()` gained an optional `search` override (it otherwise copies the *current* query string onto the redirect, which would have eaten `?timeout=1`). Client half: `components/dashboard/IdleTimeout.jsx` mounted once inside `DashboardNav` (covers all four role groups), shows a countdown modal at 5 min idle, and **any click/keypress/touch anywhere dismisses it** — deliberately NOT mousemove/scroll, or reaching for the mouse to read the modal would dismiss it. Login page split into a server wrapper + `LoginClient.jsx` (mirrors forgot-password) for the `?timeout=1` banner; `.status-info` added to globals.css; `signoutIdle()` added beside `signout()` in login/actions.ts (separate rather than a parameter, because `signout` is a form action and would receive FormData as its first arg) and both now clear the idle cookie. ⚠ **The heartbeat is load-bearing**: without `POST /api/session/keepalive` (throttled to 2 min, fired from real activity), someone *reading* one page for 10 minutes makes no requests, looks idle to the proxy, and gets signed out mid-read. Verified: 9/9 scripted probes (no cookie → fail-open + clock starts; 1/4/9 min → allowed + re-stamped; keepalive 204; 11 min → 307 + cookie cleared + **session genuinely revoked**, not just redirected; 11 min on `/api/*` → 401 JSON; banner shows on `?timeout=1` and not on plain `/login`), plus the modal driven in real Chrome by skewing `Date.now()` (appears, counts down 3:21→3:18, click-anywhere dismisses, one 204 keepalive fires on dismissal, re-arms afterwards). Throwaway users + their trigger-created profiles swept (13/13/0). ⚠ Two known limits, both accepted: the timeout is **activity-based**, so anyone who can replay the session cookie can also just keep it alive with requests — inherent to inactivity timeouts, not to this design; and a **missing** activity cookie fails OPEN (starts the clock) rather than closed, so the feature doesn't sign out every user on first deploy.

33. **Idle timeout no longer breaks password-recovery links (3 Aug, VERIFIED — 2 repro + 13 regression checks)**: second defect in Done #29, reported as "the forgot-password link expires after 10 minutes and redirects to login". Reproduced both real paths: (1) a browser with a stale `okc-last-activity` clicks the emailed reset link → `GET /auth/confirm` → **307 `/login?timeout=1`**, so the user never even saw the Continue interstitial and the still-valid token looked expired; (2) a user who reached `/change-password` and took too long over the new password → **307 `/login?timeout=1`** mid-reset. Not a hole: verifying a link mints a new session and `ok()` clears the cookie anyway (Done #31), and the recovery grant is already capped by `RECOVERY_COOKIE_MAX_AGE` (15 min) — a shorter leash than the 10-min idle budget it replaces on that one page. Verified: both repro paths now 200; the full 9-probe idle suite still 9/9; plus 4 scope checks proving the exemption is not a general bypass — `/change-password` **without** the recovery cookie still times out, **with** it is allowed, and an idle session parked on `/login` is bounced to its dashboard where the timeout still fires. ⚠ Pattern worth remembering: this and Done #31(b) are the same class of bug — the idle clock interacting badly with **session transitions** (sign-in, link verification, recovery). Any future auth entry point needs the same consideration.

## Gotchas

- ⚠ **Run `npx prisma generate` after every pull that touches `prisma/schema.prisma`.** `generated/` is a gitignored build artifact and `postinstall` only fires on `npm install`, so a schema change from a teammate leaves you with a stale client and the build fails with a confusing *type* error (3 Aug: `next build` died on `request-transaction/actions.ts:142` — "types 'FlowStatus' and '\"AWAITING_PROOF\"' have no overlap" — purely because the generated enum predated the bank-transfer migration). `npx next build` + `npx eslint .` + `npm test` are all clean once regenerated.
- ⚠ When checking build health from a shell, don't pipe `next build` into `tail` — the pipeline reports tail's exit code and a failed build looks green. Use `${PIPESTATUS[0]}`.
- Prisma Decimal is not client-serializable — always `Number()` in lib/queries.ts.
- Ledger day semantics: flows processed on day D apply at END of day D (per §8.1); seed processes Faye's deposit 16 Mar so trading starts 17 Mar with capital. P&L on a day with zero opening balance is recorded on the fund but unattributed to investors.
- `useActionState` + modal close: use the render-time "adjust state during render" pattern (see UsersClient/RequestTransactionClient), NOT setState in useEffect — the lint errors on it.
- Server actions POST through the proxy; MFA challenge/enroll runs browser↔Supabase directly (only audit goes through the server).
- Windows: case-only renames need two-step `git mv`; `npx tsc` caches via tsconfig.tsbuildinfo (delete if stale).
- Seed reads `.env` via dotenv (NOT `.env.local`) — keep the two files in sync (see env gotcha above).
- RLS is on with zero policies (Done #15), and Prisma doesn't model RLS — every future migration that CREATES a table must append `ALTER TABLE "public"."<table>" ENABLE ROW LEVEL SECURITY;` or that table is exposed via the anon REST API again. Also: supabase-js reads against an RLS-locked table return an empty 200, not an error — if a page mysteriously shows no data, check it isn't reading via supabase-js instead of Prisma.
